2. How a pixel reaches the panel

The ST7789 is a command-driven chip. You never "set pixel (x,y)"; you send a command, then parameters, then a long run of colour bytes.

Four wires, two roles

SCK, MOSIClock and data (GP10, GP11). Data is sampled on the rising clock edge, most significant bit first.
CS (GP9)Low = chip is listening. A falling edge starts a transfer.
DC (GP8)Low = this byte is a command. High = this byte is a parameter or pixel data. Read at the 8th clock of each byte.
RST (GP13)Hardware reset. BL (GP25): backlight, PWM at 5 kHz in the vendor code.

ST7789V2 datasheet §8.4.2 (command write mode), Table 6. Pins from the vendor driver.

Drawing a full frame

DC=0  send 2Ah            CASET: column range
DC=1  send x0_hi x0_lo x1_hi x1_lo   (16-bit, big-endian)
DC=0  send 2Bh            RASET: row range
DC=1  send y0_hi y0_lo y1_hi y1_lo
DC=0  send 2Ch            RAMWR: start writing frame memory
DC=1  stream 134,400 bytes  (240 × 280 × 2)

Each pixel written advances an internal address inside the window you set, so a partial update is just a smaller window and fewer bytes. That is what the vendor's Windows_show() does.

The 20-row offset

Frame memory has 320 rows; this panel shows 280. The vendor driver (and our main.py) adds 20 to the row numbers. The vendor setWindows() also computes the bottom row from the start row by mistake, so our code replaces it (firmware/rp2040/README.md).

Colour: two traps

Format. RGB565 = 16 bits: 5 red, 6 green, 5 blue. Set by command 3Ah. The datasheet says write 55h for 16-bit pixels; the vendor writes 05h. I infer the difference is in the RGB-interface bits, which an SPI display does not use. Confirm with a colour test.

Byte order. The display wants the high byte first. MicroPython's framebuf keeps 16-bit values in the RP2040's byte order, so bytes arrive swapped. The vendor constants show it: red = 0x07E0 and blue = 0xF800 are the "wrong" way round. Black (0x0000) and white (0xFFFF) are unaffected, which is why the blink works before colour is settled. The controller's MADCTL command (36h) also has an RGB/BGR bit.

Power-up order

Reset pulse, then the vendor's register settings, then 11h (sleep out) and a 120 ms wait (datasheet), then 29h (display on). Skipping the wait is a classic cause of a blank screen.

Check

DC is high during which bytes?

High means data or parameter; low means command.

Why do the row numbers get +20?

The controller memory is 320 rows tall; the panel shows 280 of them.

Which colours survive a byte-order swap unchanged?

0x0000 and 0xFFFF have identical high and low bytes. Mid grey like 0x8410 does not.
