3. SPI speed and frame rate

A full frame is 240 × 280 × 16 = 1,075,200 bits. Frame time is bits ÷ SPI clock. So the SPI clock sets the ceiling on frame rate; the question is what clock you actually get.

What the RP2040 can produce

The SPI block divides its input clock clk_peri: rate = clk_peri / (CPSDVSR × (1 + SCR)), with CPSDVSR even from 2 to 254 and SCR from 0 to 255. The fastest master rate is clk_peri / 2. The datasheet's own example: 125 MHz in, 62.5 MHz out.

RP2040 datasheet, SPI section (SSPCLKOUT, "Bit rate generation").

What MicroPython sets by default

The MicroPython RP2 quick reference says machine.freq(mcu, peripheral=48_000_000): the peripheral clock defaults to 48 MHz, and it can only be 48 MHz or equal to the CPU clock (125 MHz at boot). If SPI runs from 48 MHz, the ceiling is 24 MHz, not the 100 MHz the vendor code asks for. A request above the limit is not an error in itself; MicroPython's SPI docs say the actual rate can differ from the request, so print the SPI object.

This is a reading of the documents, not a measurement. Our docs/hardware/display-frame-rate.md assumes 62.5 MHz and a 58 fps ceiling. That needs machine.freq(125_000_000, 125_000_000) first, and our notes say the ST7789 minimum write cycle (16 ns) is exactly 62.5 MHz, with no margin. benchmark_display.py settles it.

Try it

Try 48 → 24 MHz → 22 fps. Then 125 → 62.5 MHz → 58 fps. Then 125 with a 40 MHz request: the best available is 31.25 MHz, 29 fps, just under 30. Rates fall in steps, not smoothly.

The calculator assumes the driver picks the closest rate not above the request. That is my assumption about the driver; the formula is the datasheet's.

Why it still isn't the animation rate

This is transfer only. Reading frames from flash, decoding them, and Python overhead all add time. Uncompressed 30 fps is 32.3 Mbit/s of pixels, so a changed-region update or compression is needed (see display-frame-rate.md).
